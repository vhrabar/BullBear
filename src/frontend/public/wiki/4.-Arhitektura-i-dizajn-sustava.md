## Opis arhitekture

### Stil arhitekture
Odabrani stil arhitekture je klijent–poslužitelj s elementima uslužno orijentiranog sustava.
Frontend (React) djeluje kao klijent, dok Django REST Framework backend predstavlja poslužitelj koji izlaže REST API sučelje putem HTTP protokola. Time se omogučuje potpuno razdvajanje tih dviju komponentni s ciljem lakšega razvoja, boljega ispitivanja usred manje međuovisnosti, lakšega horizontalnoga skaliranja u fazi deploymenta s ciljem uštede, itd. Uporaba REST principa omogučuje jednostavnu, te univerzalnu komunikaciju između različitij dijelova sustava,

### Podsustavi

### Deployment
Aplikacija će se nalaziti na DigitalOcean droppletu, povezana s GitHub repozorijem putem posebno definiranih akcija. Različiti servisi (AWS, MS Azure, Heroku, itd.) omogućuju iste/slične funkcionalnosti, mogućnosti konekcije, itd.; ali je ova platforma odabrana jer ne ograničava studente u dostupnosti opcija (poput nekih koje studente ograničavaju na single-core instance), te nudi $200 USD u kreditima za svakoga studenta.

### Baza Podataka

### Mrežni protokoli
#### HTTP
Protokol HTTP(S) koristi se za komunikaciju između React frontenda i Django-REST backenda.  
React aplikacija upućuje RESTful API zahtjeve (GET, POST, PUT, PATCH, DELETE) prema definiranim Django-REST endpointima, dok backend vraća JSON odgovore koje React interpretira i prikazuje korisniku.

---

#### ORM
Komunikacija između Django-REST backenda i PostgreSQL baze podataka odvija se putem ORM (Object–Relational Mapping) sloja;
ORM prevodi Python kod u SQL naredbe, te prima odgovore iz baze, koje zatim pretvara natrag u Python objekte.  

---

#### WebSocket
Za real-time funkcionalnosti, poput chat sustava, notifikacija ili dinamičkog ažuriranja podataka, koristi se WebSocket protokol.  
Django, putem ASGI sučelja i biblioteka poput Django Channels, omogućuje dvosmjernu, trajnu vezu između klijenta i poslužitelja, što omogućuje neprekidnu razmjenu podataka bez potrebe za ponovnim učitavanjem stranice.

---

#### ASGI
Komunikacija između web-poslužitelja i Django aplikacije odvija se putem ASGI(Asynchronous Server Gateway Interface)  sučelja, koje podržava sinhronu i asinkronu komunikaciju uz posredstvo WebSocket nad-protokola. Time se tvori veza između Django aplikacijskoga sloja i HTTP zahjteva koje prima sam poslužitelj

### Glavni Upravljački Tok

Tok započinje na REACT sučeklju, korisničko interakcijom s nekom vizualnom komponetnom (primjerice, obrascem za kupnju), pri čemu se šalje RESTfull API zahtjev Django-REST backendu putem HTTPS protokola, kojega prihvaća HTTP server. Potom, Django-REST backend prima zahjtev putem ASGI sučelja, gde ga odgovarajući view i serializer, odabarni preko URL uzorka, obrađuju.

Ako je potrebno pristupiti bazi podataka, backend koristi ORM sloj koji pretvara aplikacijski upit u SQL naredbu i prenosi ga PostgreSQL bazi, koja upit izvršava, te vraća rezultat putem ORM sloja, kojai ih prevodi natrah u Python objekte. Potom, serializer te objekte pretvara u JSON format prikladan za prijenos prema klijentu.

Backend potom vraća  odgovor koji sadrži JSON podatke putem ASGI sučelja HTTP serveru, koji frontentu vraća taj odgovor putem HTTPS protokola. React aplikacija prima taj odgovor, ažurira stanje  ili globalni kontekst te prikazuje dobivene informacije korisniku u web pregledniku.  
U slučajevima gdje je potrebna stalna komunikacija u stvarnom vremenu, React i Django održavaju trajnu vezu putem WebSocket protokola, što omogućuje dvosmjerni prijenos podataka bez ponovnog učitavanja stranice.

Ciklus se završava povratnom informacijom korisniku; ažuriranim prikazom, porukom o uspjehu ili prikazom novih podataka, čime se zatvara puni krug komunikacije između korisnika, aplikacijskog sloja i baze podataka.

## Obrazloženje odabira arhitekture

Odabrani stil arhitekture temelji se na klijent–poslužitelj modelu s elementima „decoupled” pristupa. Frontend (React) je u potpunosti odvojen od backend sustava (Django REST Framework), što omogućuje neovisni razvoj, jednostavnije testiranje i lakšu nadogradnju pojedinih dijelova sustava. Ovakav stupanj razdvajanja smanjuje međuovisnosti između podsustava te povećava fleksibilnost i skalabilnost cijeloga rješenja. REST API komunikacija dodatno osigurava standardizirano i lako proširivo sučelje između komponenti.

Arhitektura je odabrana kako bi zadovoljila zahtjeve modularnosti, održivosti i jednostavne distribucije. Korištenje PostgreSQL baze podataka omogućuje stabilno i performantno upravljanje trajnim podacima, dok Nginx djeluje kao reverse proxy i poslužitelj statičkih datoteka (npr. CSS), čime rasterećuje backend. Cijeli se sustav izvodi kroz tri Docker kontejnera — frontend, backend i Nginx — što pojednostavljuje deployment, izolira procese i omogućuje lakše skaliranje prema potrebi.

• Izbor arhitekture temeljen na principima oblikovanja:

1. Visoka kohezija: svaki podsustav ima jasno definiranu odgovornost (UI, poslovna logika, pohrana podataka, poslužitelj statičkih resursa).

2. Niska povezanost: React i Django REST API komuniciraju isključivo putem HTTP zahtjeva, što omogućuje zamjenu ili nadogradnju jedne strane bez utjecaja na drugu.

3. Fleksibilnost i proširivost: REST API omogućuje jednostavno dodavanje novih endpointa i funkcionalnosti bez promjene postojeće strukture.

4. Održivost: jasan razdjeljen dizajn pojednostavljuje održavanje i buduće izmjene.

5. Skalabilnost: Docker te odvojen frontend/backend olakšavaju horizontalno skaliranje pojedinih dijelova sustava.

Ovi principi omogućuju da arhitektura zadovolji potrebe projekta uz minimalnu kompleksnost, ali uz jasnu mogućnost nadogradnje u budućnosti.

• Razmatrane alternative

Razmatran je i mikroservisni pristup, koji bi u teoriji pružio još bolju skalabilnost i granularnu kontrolu nad podsustavima. Ipak, takva arhitektura donosi znatnu složenost u pogledu orkestracije, komunikacije između servisa i održavanja. S obzirom na veličinu tima i opseg projekta, mikroservisna arhitektura ocijenjena je kao prekomplicirana i nepotrebno skupa. Stoga je odabran jednostavniji, ali dovoljno fleksibilan klijent–poslužitelj model s jasno odvojenim podsustavima.

## Organizacija sustava na visokoj razini

Sustav je organiziran prema klijent–poslužitelj arhitekturi, pri čemu se frontend i backend izvode kao odvojeni, ali međusobno povezani podsustavi. Arhitektura naglašava modularnost i neovisnost komponenti, što olakšava razvoj, testiranje i održavanje.

• Klijent–poslužitelj

Frontend implementiran u Reactu djeluje kao klijent koji šalje HTTP zahtjeve prema backendu. Backend, izgrađen pomoću Django REST Frameworka, djeluje kao poslužitelj i izlaže REST API koji omogućuje dohvat, obradu i izmjenu podataka. Klijent komunicira isključivo preko API endpointa, čime se postiže potpuno “decoupled” interakcija i neovisnost između korisničkog sučelja i poslovne logike.

• Baza podataka

Sustav koristi PostgreSQL, relacijsku bazu podataka smještenu unutar zasebnog Docker kontejnera. Baza podataka služi za trajnu pohranu svih ključnih entiteta sustava (korisnici, zapisi, konfiguracije i ostali poslovni podaci). Backend pristupa bazi preko ORM sloja, čime se osigurava dosljednost, integritet podataka i jednostavno upravljanje upitima.

• Datotečni sustav

Statički resursi koji se ne pohranjuju u bazu – poput generiranih datoteka, CSS-a, JavaScript builda i drugih statičkih sadržaja – smješteni su na datotečnom sustavu koji poslužuje Nginx. Nginx djeluje kao reverse proxy koji prosljeđuje API zahtjeve backendu, dok istovremeno preuzima odgovornost za posluživanje statičkih datoteka radi bolje optimizacije performansi.

• Grafičko sučelje

Korisničko sučelje implementirano je kao web aplikacija u Reactu. Ono se izvršava u pregledniku korisnika i prikazuje podatke preuzete putem REST API-ja. GUI je u potpunosti odvojen od backend logike, a integracija se odvija isključivo putem mrežne komunikacije. Takav pristup omogućuje jednostavnu nadogradnju sučelja, brzu iteraciju te mogućnost razvoja alternativnih klijenata (npr. mobilne aplikacije) bez promjene backend dijela sustava.

## Organizacija aplikacije

![Component Diagram1](https://github.com/user-attachments/assets/57ebd5fe-7586-4ec6-bfa1-4d940b10fa1a)

Aplikacija je strukturirana kao skup posve odvojenih, ali povezanih cjelina: Django-REST backend, React frontend i servis za periodičko ažuriranje tržišnih vrijednosti. Takva izolacija omogućuje kvalitetnu implementaciju principa separacije odgovornosti, veću otpornost na pogreške i olakšani razvoj. Svaka cjelina obavlja strogo definiranu ulogu u cjelokupnoj arhitekturi, a međusobna se komunikacija svodi na standardizirane protokole (REST, ORM, ASGI).

Tradicionalne Django aplikacije slijedi obrazac nalik MVC paradigmi (točnije M–Template–C model), međutim u ovoj implementaciji prezentacijski sloj u potpunosti je izdvojen u React sloj, čime se Django backend reducira isključivo na ulogu API poslužitelja. React frontend i Django REST backend međusobno komuniciraju isključivo putem REST API poziva, što omogućuje potpunu neovisnost dvaju slojeva. Takvo strukturiranje omogućuje da se frontend i backend razvijau posve nezavisno, što značajno olakšava testiranje i sam razvoj.

Pomoćni servis za ažuriranje vrijednosti predstavlja dodatnu komponentu koji djeluje nezavisno od glavnih cjelina, pristupajući bazi podataka izravno, zaobilazeći Django-REST sloj, ubrzavajući proces pristupa i smanjući opterećenje samoga sustava. 

### Backend
Django REST backend dodatno je organiziran u dvije glavne komponentne; core-api i api.
Core-api osigurava glavnu konfiguraciju, globalne postavke,i rutiranje prema api podsustavima. 
Kompleksniji dio strukture nalazi se u modulu api, koji je podijeljen u jasno definirane pod-komponente; api.users, api.trading, api.leaderboard, api.subscription itd.. Svaka od tih cjelina funkcionira kao polu-neovisna jedinica s vlastitim modelima, serializerima, viewovima i rutama. Premda dijele jedinstvenu bazu podataka, te postoji određena komunikacija između njih, u pravilu djeluju kao semi-neovisne cjeline.

Ovakav način organizacije pridonosi jednostavnosti sustava, jednostavnijem otklanjanju pogrešaka te bržem razvoju novih funkcionalnosti. Modularni pristup omogućuje razvoj specifičnim dijelova sustava bez narušavanja stabilnosti ostalih. Nadalje, precizna podjela omogućuje da se pojedine cjeline potencijalno izdvoje u zasebne usluge u kasnijim fazama razvoja, ili se lako zamjene drugima.

### Frontend
React frontend strukturiran je modularbno, gdje se veće cjeline (stranice) sastoje od manjih, višekratno upotrebljivih komponenti. Tijekom procesa izgradnje sve se komponetne objedinjene u jedinstvenu SPA strukturu, čime se zadržavaju sve prednosti modernih klijentske aplikacije poput dinamičkoga učitavanje sadržaja bez potreba za ponovnim učitavanjem stranica te mogućnost.

Cjelokupni sustav zasniva se na kombinaciji monolitnog i mikroservisnog pristupa, preuzimajući najbolja svojstva svakoga od tih načina podjele.

# Dinamičko ponašanje aplikacije

Dinamičko ponašanje aplikacije odnosi se na način na koji objekti u
sustavu evoluiraju kroz vrijeme, uključujući prijelaze između različitih
stanja. To uključuje aktivnosti, događaje, odluke i interakcije unutar
aplikacije. UML dijagrami stanja omogućuju vizualizaciju tih promjena i
olakšavaju razumijevanje dinamike sustava.

Razumijevanje promjena stanja neophodno je za pravilno funkcioniranje
aplikacije jer pruža uvid u interakcije među objektima, komponentama i
korisnicima tijekom rada sustava. Korištenjem UML dijagrama stanja i
aktivnosti moguće je vizualizirati prijelaze i stanja objekata,
identificirati potencijalne probleme, osigurati točnu implementaciju te
poboljšati komunikaciju među članovima tima.

**Zadatak:**

- Dokumentirajte dva dinamička dijagrama koji prikazuju značajne ili
  neke složene procese u aplikaciji. Registracija i prijava korisnika
  nisu ključni procesi u ovom kontekstu, stoga se usmjerite na
  specifične, značajne procese.

## UML dijagrami stanja

UML dijagrami stanja nužni su za razumijevanje dinamičkog ponašanja
sustava. Oni jasno prikazuju promjene stanja objekata tijekom vremena
ovisno o događajima i uvjetima.

**Preporuke za izradu UML dijagrama stanja:**

1.  Odaberite značajan objekt sustava (npr. prijava štete, obrada
    zahtjeva).

2.  Identificirajte stanja objekta (npr. aktivan, neaktivan, obrisan).

3.  Definirajte događaje i uvjete prijelaza.

4.  Ako je potrebno, koristite hijerarhiju stanja za složenije probleme.

5.  Dodajte bilješke za pojašnjenje važnih prijelaza i elemenata.

>> Primjer: Dijagram stanja za prijavu štete može uključivati:

>> - Stanja: *Kreirana prijava*, *Obrađena prijava*, *Zatvorena prijava*….

## UML dijagrami aktivnosti

Dijagram aktivnosti prikazuje tijek izvršavanja određenog procesa. Osim
za razumijevanje toka podataka unutar aplikacije, koristi se za analizu
poslovnih procesa.

**Zadatak:**

1.  Identificirajte proces koji želite modelirati (npr. obrada
    zahtjeva).

2.  Razlomite proces na aktivnosti i povežite ih za prikaza slijeda
    izvršavanja.

3.  Upotrijebite pseudo čvorove za jasan prikaz.

>> Primjer:** Na primjer, u aplikaciji za upravljanje štetama, dijagram aktivnosti može prikazivati proces obrade zahtjeva za pomoć, što
uključuje aktivnosti: *Primanje zahtjeva*, *Analiza podataka*, *Odobravanje resursa*, *Slanje pomoći*.
